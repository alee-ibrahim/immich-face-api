The face API answers one question: who is in this photo? Send a photo; get back each face with a box and the named person it most likely shows, or null. Results are suggestions for a person to confirm, never automatic tags.

Quick start

  1. Base URL: {{ base }}
  2. Get a key: Apps & keys → enter the app's name, owner and a label → Create key. Copy the key at once: it is shown only that one time. Put it in the calling app's secret store (never in code or a browser).
  3. First call (keep the key in an environment variable, not on the command line):
{{ block('export FACE_API_KEY="$(cat face-api.key)" # the key you copied, saved to a file curl -sS "' ~ base ~ '/v1/identify" \\ -H "Authorization: Bearer $FACE_API_KEY" \\ -F image=@photo.jpg') }}

You get 200 with a faces list (possibly empty). 401 means the key is wrong or revoked.

Authentication

Every /v1 call needs the API key, in either header (one is enough):

{{ block('Authorization: Bearer ifa_1a2b3c4d_ X-API-Key: ifa_1a2b3c4d_') }}
  • Format: ifa_<8 hex prefix>_<43 random characters>. The prefix identifies the key in this admin (shown as ifa_1a2b3c4d_…); the service stores only a SHA-256 of the whole key, so a lost key cannot be recovered, only replaced. Keys configured by the deployment's environment (no ifa_ prefix) work the same way.
  • Per key: an app name (usage is counted per app), owner, label, optional rate limit and expiry.
  • Rotation: create a second key for the same app, switch the app to it, check Last used, then revoke the old one. No downtime.
  • Revoke: Apps & keys → Revoke. Calls with it fail with 401 within about 30 seconds. Expired keys fail the same way.
  • The key is checked before the photo is read, so a request without a valid key costs nothing.

POST /v1/verify

Re-check stored tags: send a photo and the person_id(s) it is tagged with (at most {{ lim.verify_claims }}). For each claimed person you get the distance from the nearest face in the photo to that person's faces, whether it is within the threshold, and who the best match for that face is now. A box from an earlier identify compares only that face. Merged people are followed to the person they were merged into. Same key, limits and logging as identify; the photo is not stored.

{{ code([ ('curl', 'curl', 'curl -sS "' ~ base ~ '/v1/verify" -H "Authorization: Bearer $FACE_API_KEY" \\ -F image=@photo.jpg -F person_id=6f1c1f0e-8d0a-4c55-9d43-4f0b1d1f2a10 -F box=0.41,0.18,0.06,0.10'), ('php', 'PHP / Laravel', '$r = Http::withToken(config(\'services.face_api.key\'))->timeout(120) ->attach(\'image\', $bytes, \'photo.jpg\') ->post(\'' ~ base ~ '/v1/verify\', [\'person_id\' => $tag->immich_person_id]) ->throw()->json(); $claim = $r[\'claims\'][0]; // verdict: match | match_not_best | no_match | no_face | no_reference | person_gone'), ]) }}

GET /healthz

No key needed. 200 {"status":"ok"} while the service runs; use it for your own uptime check.

Limits

LimitValue
Photo sizeup to {{ lim.max_mb }} MiB per request (a gateway in front may stop larger bodies earlier); send a web-size copy, 2000–3000 px is plenty: faces are detected on a {{ lim.max_edge }} px version anyway
Pixelsup to {{ lim.max_mp }} megapixels, checked before decoding
FormatsJPEG (including camera files with an embedded preview), PNG, WebP, HEIC/HEIF. Animated images: first frame only
Rate{{ lim.rate }} requests/minute per key (burst {{ lim.burst }}) unless the key has its own limit; per service instance. A gateway may add a per-IP limit
Timeusually 1–3 s per photo; allow 120 s client timeout. A photo waits at most {{ lim.queue_timeout }} s for a free slot (then 503) and {{ lim.ml_timeout }} s for face detection

Errors

Errors are JSON: {"error": {"code": "...", "message": "..."}}, with a Retry-After header on 429 and 503.

StatusCodeMeaningWhat to do
400bad_request, invalid_imageno image field, bad query, or a file that is not a valid imagefix the request; do not retry
401unauthorizedkey missing, wrong, revoked or expiredcheck the key; alert the maintainers; do not retry in a loop

Best practices

  • Server side only. Call the API from your back end, never from JavaScript in a browser: the key would leak, and the API sends no CORS headers on purpose. Keep the key in your platform's secret store or encrypted environment variables, never in a repository, a front-end bundle or a log line.
  • Suggestions, confirmed by staff. Store the answer as pending suggestions. Show each box with the name as a question ("Jane Example? ✓ ✗"); show the candidates when ambiguous is true; leave unknown faces for staff to name or skip. Publish only confirmed tags, stored in your own database with the person_id, the name at confirmation time, who confirmed and when. Keep rejected suggestions so a re-run does not ask again.
  • Call once per photo, cache the answer. Run it in a background job when a photo is added, not on every page view. Re-run only when you want fresh suggestions (for example after many people were named). Refresh display names from GET /v1/people by person_id (for example nightly) instead of re-identifying.
  • Retries with backoff. Retry only 429, 502 and 503, at most a few times, honouring Retry-After. Never retry 400, 401, 413 or 415. Your own upload flow must never depend on this API: tagging can always wait.
  • Send a reasonable copy. A 2000–3000 px JPEG is faster and gives the same result as a 25 MB original.
  • Privacy. Faces are biometric data. The API never stores your photos; what it keeps for its admins is listed under Privacy. Do the same in your app: do not keep face crops or the raw answers longer than needed, and do not build a public "find this face" search. Only people a curator named in the archive can be returned.

Privacy: what this service stores

The uploaded photo is never stored: it is decoded in memory, sent to face detection and dropped. For its admins, this deployment keeps:

{% if lim.changes %}{% endif %}
Hourly countsrequests, faces, matches, errors and latency per app and hour. No names. Kept for the usage retention (default 400 days)
Request log{{ "on" if p.request_log else "off" }}{% if p.request_log %}, kept {{ p.request_days }} days{% endif %}: per verify call the time, app, status, latency, image size and counts only; per identify call the time, app, status or error code, latency, image size in bytes and pixels, the number of faces matched, unknown, ambiguous and near the threshold, and per face (at most {{ p.max_faces }}) its box, the matched name, person id and distance and the nearest named people with their distances
People change logids and names of the archive's named people, which named person each face belongs to (ids only), and the change events, kept {{ lim.changes_days }} days. No images, no embeddings
Face crops{{ p.crops }}{% if p.crops != "none" %}, kept {{ p.crop_days }} days: a {{ p.crop_size }} px JPEG of {{ "every detected face" if p.crops == "all" else "each unknown, ambiguous or near-threshold face" }} (a new image, no metadata) and its face embedding, so curators can name missed people. Crops and embeddings are biometric data{% endif %}
  • Only signed-in admins see it (Requests, Missed faces). Crops are served only here, never cached by the browser, and never through the API host.
  • Old entries are deleted automatically (checked every few hours). Delete now: Requests → Stored data → type DELETE (crops only, or the whole log); each deletion is recorded with who did it. On the command line: python -m immich_face_api purge --crops --yes or --all --yes.
  • Switch off: FACE_API_STORE_CROPS=none (no crops), FACE_API_REQUEST_LOG=false (no request log); retention with FACE_API_REQUEST_LOG_RETENTION_DAYS and FACE_API_CROP_RETENTION_DAYS. Set them on the API (it writes the log) and the admin (it shows the settings).
  • Whether keeping this is lawful (consent, purpose, retention, informing people, an impact assessment) is the responsibility of whoever runs the service.
