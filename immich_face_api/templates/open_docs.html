Face API reference

The face API answers one question: who is in this photo? Send a photo; get back each face with a box and the named person it most likely shows, or null. Results are suggestions for a person to confirm, never automatic tags. It is a server-to-server API: call it from your back end only.

How to build a tagging feature on top of it (storing tags, nightly sync, re-checking, profile pages, privacy): Integration guide.{% if lim.openapi %} Machine-readable description: openapi.json (OpenAPI 3.1).{% endif %}

Quick start

  1. Base URL: {{ base }}
  2. Get an API key: keys are issued by the operator of this service. Contact them with your app's name and a technical contact; you get one key per app (and a separate one for each test or staging environment). The key is shown once: put it straight into your server's secret store or encrypted environment variables.
  3. First call (keep the key in an environment variable, not on the command line or in code):
{% set c %} export FACE_API_KEY="$(cat face-api.key)" # the key you were given, saved to a file curl -sS "{{ base }}/v1/identify" \ -H "X-API-Key: $FACE_API_KEY" \ -F image=@photo.jpg {% endset %}{{ m.block(c) }}

You get 200 with a faces list (possibly empty). 401 means the key is missing, wrong, revoked or expired.

Authentication

Every /v1 call needs the API key, in either header (one is enough):

{% set c %} X-API-Key: Authorization: Bearer {% endset %}{{ m.block(c) }}
  • The key is checked before the photo is read, so a request without a valid key is rejected at once with 401 and WWW-Authenticate: Bearer.
  • Usage and rate limits are counted per app (per key).
  • Rotation: ask the operator for a second key for the same app, switch your app to it, then ask them to revoke the old one. No downtime.
  • The key is a secret. Use it only from your server: never in a browser, a mobile app, a front-end bundle, a repository or a log line. The API sends no CORS headers on purpose. If a key leaks, tell the operator so it can be revoked (revoked keys fail within about 30 seconds).
  • GET /healthz{% if lim.openapi %} and GET /openapi.json{% endif %} need no key.

Main subject: who the photo is about

Recognising someone is not the same as the photo being about them. Each face gets a role: main (the portrait, the speaker at the podium), co_subject (one of two or a few people the photo is about: a handshake, a small group posing) or background (the audience, people behind, small or blurred faces, one of many in a crowd shot), and a prominence from 0 to 1. It is measured from the photo itself: face size and how much it stands out from the other faces, sharpness, position in the frame, faces cut by the edge, exposure and the number of faces. {% if lim.subject == "always" %}It is on by default; ?subject=0 skips it.{% else %}Add ?subject=1 to get it.{% endif %}

  • Profile pages: to list a person's photos, use the photos where that person's person_id has role main or co_subject; main only for photos about that person alone.
  • Verify: add subject=1 to POST /v1/verify; each claim then says is_main_subject, with the face's role and prominence.
  • Store the role with the confirmed tag, and the subject_model_version: when the weights are recalibrated you can re-check old photos with verify.

POST /v1/verify

Re-checks claimed people (for example tags you stored months ago) against a photo. For each claimed person_id you get the distance from the nearest face in the photo to that person's faces, whether it is within the threshold, and who the best match for that face is now. Same key, limits and pipeline as identify; the photo is not stored.

POST /v1/verify/batch

Several photos in one JSON body, the images base64-encoded: at most {{ lim.verify_batch }} items and {{ lim.max_mb }} MiB per call (base64 adds a third). One rate-limit token per photo. The answer is {"items": [...]} in order, each a verify response plus your ref, or {"ref", "error"} for a bad item; the batch stops on 429/502/503. It saves round trips, not work.

Retries: a full example

Retry only 429, 502 and 503, a few times, honouring Retry-After. Never retry 400, 401, 413 or 415.
