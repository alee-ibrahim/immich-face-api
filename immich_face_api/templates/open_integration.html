Integration guide

How to add "who is in this photo" to your website or app: the face API suggests, your staff confirm, and your app keeps the confirmed tags in its own database, linked to its own people (members, staff, guests).

Base URL: {{ base }}. Every call needs an API key, issued by the operator of this service: contact them for one (one key per app and environment). Endpoint details are in the API reference.

How it fits together

  1. The photo archive holds the photos and the named people (named by its curators). Each named person has a stable person_id. The face API only reads it.
  2. Your app sends a photo to POST /v1/identify and gets suggestions: a box per face and the named person it most likely shows.
  3. Your staff confirm or correct the suggestions in your app's admin. Only confirmed tags are published.
  4. Your app maps each person_id to your own id (a member id, for example), keeps that mapping up to date{% if lim.changes %} with the nightly change feed{% endif %}, and re-checks tags with POST /v1/verify when the archive changes.

What to store

A minimal schema (adapt the names and types to your framework):

Members and person ids

  • Store your own id. Your pages, search and profiles use your member id, never the archive's person_id or name directly. The person_id is the link between the two.
  • One member, many person ids. The archive can hold the same person as several groups of faces (different years, different photographers, a split that was not merged back). Map each of them to the same member. When identify returns a person_id you have not mapped yet, show it to staff as "map to which member?".
  • Names are display only. The archive's spelling can change (see renamed); your member record stays the source of truth for your site.
  • Mapping is a staff decision: do not map automatically by name, even when the names look identical.

Suggest, then confirm

  1. When a photo is added, queue a background job that calls POST /v1/identify?candidates=3 once and stores each face as a pending suggestion. Never call it while rendering a page.
  2. In your admin, draw each box on the photo with the suggested name as a question ("Jane Example? ✓ ✗"). When ambiguous is true, show the candidates and pre-select nobody. Unknown faces (person_id null) are for staff to tag by hand or skip.
  3. On ✓, write a photo_tags row with your member id (via the mapping), the person_id, the box, the role, who confirmed and when. On ✗, mark the suggestion rejected so a re-run does not ask again.
  4. Staff-confirmed tags are authoritative. No later API answer (identify, verify or a change event) may overwrite or delete a confirmed tag automatically: at most flag it with needs_review for staff.
  5. confidence is a hint, not a probability: never auto-confirm on it.

Profile pages

A member's profile should show photos about that member, not every crowd shot they appear in. Use the role stored with the confirmed tag:

{% set c %} -- photos for a member's profile page: the photo is about them (alone or with a few others) SELECT p.* FROM photo_tags t JOIN photos p ON p.id = t.photo_id WHERE t.member_id = :member AND t.role IN ('main', 'co_subject') ORDER BY p.taken_at DESC; {% endset %}{{ m.block(c) }}
  • role = 'main' only: photos about that person alone (a portrait for a header image, for example).
  • background tags are still useful for search ("all photos with this member"), just not for the profile.
  • Staff may correct the role when confirming. Keep subject_model_version with the tag so you can re-score older photos later with POST /v1/verify and subject=1.

Nightly sync

The archive's curators keep naming, merging and splitting people. Once a night (or more often), read GET /v1/people/changes from your saved cursor and apply each event:

EventWhat to do
renamedupdate archive_name in your mapping. Tags and members stay as they are.
mergedthe person from_person_id is gone; its faces are now into_person_id. Point your mapping's from_person_id rows to into_person_id (if both were mapped to different members, flag it for staff instead). Pending suggestions: rewrite the id.
faces_moveda split or correction: count faces went from from_person_id to to_person_id. Re-check the tags and pending suggestions of from_person_id with verify; offer to_person_id as an alternative; if to_person_id is new to you, ask staff which member it is.
deletedthe person was deleted, hidden or un-named (reason). Stop suggesting it, drop its pending suggestions, set the mapping's status, and flag (do not delete) its confirmed tags for review.
createda newly named person: offer it to staff for mapping to a member; optionally re-run identify on recent untagged photos.

Re-checking tags

POST /v1/verify answers "is this person still in this photo, and still the best match?" for tags you already have. Use it after {% if lim.changes %}a faces_moved or merged event, {% endif %}after a long time, or before publishing older unconfirmed suggestions. Send the stored box so only that face is compared; POST /v1/verify/batch takes up to {{ lim.verify_batch }} photos per call.

verdictUnconfirmed suggestionStaff-confirmed tag
matchkeepkeep
match_not_bestreplace with best_person_id as a new suggestionkeep, flag for review
no_match, no_facedropkeep, flag for review
person_gone, no_referencedropkeep, flag for review

Confirmed tags are never removed by a verify result: a person decided, so a person reviews.

Server side only

  • Never call the API from a browser or a mobile app. The key would be visible to anyone; the API sends no CORS headers on purpose. Your back end calls it; your pages read your own database.
  • Keep the key in your platform's secret store or encrypted environment variables (for example FACE_API_KEY and FACE_API_URL), never in a repository, a front-end bundle, an error report or a log line. Use a separate key for each environment (production, staging, local development).
  • Never put the key in a URL query string. Send it in the X-API-Key or Authorization header.
  • If a key leaks, ask the operator to revoke it and issue a new one; rotation needs no downtime.

Reliability

  • Your upload flow must never depend on this API: tagging can always wait. Call it from a queue with a 120 s timeout.
  • Retry only 429, 502 and 503, a few times, waiting Retry-After seconds. Never retry 400, 401, 413 or 415.
  • Stay under {{ lim.rate }} requests per minute per key (burst {{ lim.burst }}): for a backlog of old photos, run one worker and let Retry-After pace it.
  • Send a web-size copy (2000–3000 px JPEG), not the original: faster, same result. Limit: {{ lim.max_mb }} MiB.
  • Call identify once per photo and keep the answer; refresh names from the change feed, not by re-identifying.

Privacy

  • Faces are biometric data. Treat suggestions, boxes and person ids as personal data in your app: restrict who can see pending suggestions, and delete rejected or stale suggestions you no longer need.
  • Only people the archive's curators named can be returned. Unknown faces stay unknown: do not build a public "find this face" or upload-a-selfie search on top of the API.
  • Publish only confirmed tags. Honour removal requests: remove the tag in your app, and tell the operator if the person should also be un-named in the archive.
  • What this service keeps: your uploaded photo is never stored (it is processed in memory and dropped). {% if lim.request_log %}A request log (time, app, status, image size, which named people were matched, and the distances) is kept for {{ lim.request_days }} days{% if lim.crops != "none" %}, and small face crops are kept for {{ lim.crop_days }} days so the archive's curators can name missed people{% endif %}. {% endif %}Hourly usage counts per app contain no names.
  • Whether and how you may tag people (consent, purpose, informing them) is also your app's responsibility; follow your organisation's data protection policy.
